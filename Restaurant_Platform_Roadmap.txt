1 Restaurant Platform Phase-wise Roadmap

Prepared for Narender Kumar | 12 October 2026 | Version 2.0

Project goal
Build a multi-restaurant SaaS platform that supports restaurant onboarding, table QR ordering, live kitchen operations, staff workflows, billing, payments and platform administration. The MVP will focus on a single active branch per restaurant, Android staff mobile app, and core guest ordering flows.

Recommended technology stack
- Backend: Laravel (PHP)
- Web frontend: React + TypeScript
- Mobile app: Capacitor + React
- Database: MySQL
- Cache and queue: Redis
- Realtime: Laravel Reverb / Echo
- Storage: object storage for menu images and QR receipts
- Deployment: Nginx + PHP-FPM + queue workers + WebSocket service

Strategy
Use a modular monolith for MVP. Keep domain modules separate: Identity, Tenancy, Catalog, Tables, Ordering, Billing, Payments, Subscriptions, Notifications and Reporting. Do not split into microservices before there is real load and team scale. Most product risk is in business rules, auth, payment flow and concurrency, not service boundaries.

Phase wise plan

Phase 0: Discovery and decision making
Duration: 1 week
Goal: finalize business rules and technical constraints before coding.

Tasks
- Finalize MVP scope and exclusions
- Define restaurant ownership, staff roles and permissions
- Decide payment model: restaurant-owned merchant account vs platform-managed flow
- Finalize branch scope: one active branch per restaurant for MVP
- Confirm target devices: Android staff app first
- Decide guest flow: QR scan, table session, PIN rules, guest join policy
- Confirm tax and refund policy for local compliance
- Finalize tech stack and environment setup

Deliverables
- Approved MVP scope
- Role and access matrix
- Payment ownership decision
- Architecture decision record
- Technical backlog prioritization

Exit gate
- Business rules signed off
- Payment model decided
- MVP backlog approved

Phase 1: Foundation and architecture setup
Duration: 2 weeks
Goal: establish codebase structure, auth, tenancy rules, CI and local environment.

Tasks
- Create Laravel project and repo structure
- Set up Git, CI/CD, linting and testing pipeline
- Implement tenant-aware database architecture
- Add authentication and session security
- Define authorization policies and role permissions
- Set up MySQL schema baseline and migrations
- Configure Redis for cache and queue processing
- Set up Laravel Reverb for live event testing
- Define API versioning and OpenAPI contract baseline
- Create developer onboarding document

Deliverables
- Working Laravel backend skeleton
- Tenant isolation framework
- Auth + RBAC baseline
- CI pipeline
- API contract started

Exit gate
- All core auth and access layers working
- Tenant data isolation verified
- CI pipeline passes basic checks

Phase 2: Restaurant onboarding and configuration
Duration: 2 to 3 weeks
Goal: allow restaurant owners to set up their restaurant, staff, tables and menu.

Tasks
- Restaurant profile creation and approval flow
- Branch creation and settings
- Currency, timezone and store configuration
- Staff invitation and role assignment
- Menu category and item setup
- Variant and modifier management
- Table creation and section setup
- QR generation and regeneration
- Branch menu availability rules
- Test order preparation checklist

Deliverables
- Restaurant onboarding flow
- Staff management screens
- Table configuration and QR export
- Menu editor with variants and modifiers
- Restaurant status lifecycle

Exit gate
- A new restaurant can be created, configured and tested
- Restaurant A cannot access Restaurant B data
- QR token regeneration invalidates old links

Phase 3: Customer ordering MVP
Duration: 2 to 3 weeks
Goal: make QR-based table ordering work end-to-end for guests.

Tasks
- QR scan landing page and restaurant/table validation
- Guest session join and PIN flow
- Menu browsing and item detail view
- Cart and quantity management
- Variant and modifier selection
- Total calculation and checkout quote
- Idempotent order submission
- Order tracking page
- Service requests: call waiter, water, bill request
- Error states and connectivity messaging

Deliverables
- QR customer ordering flow
- Guest session system
- Order submission with retry safety
- Order tracking page
- Service requests module

Exit gate
- A guest can scan QR, order and track order status
- Double submit is prevented
- Closed session cannot create new orders

Phase 4: Kitchen and live order operations
Duration: 2 weeks
Goal: create operational workflows for restaurant staff and kitchen teams.

Tasks
- Order state machine implementation
- Queue view for kitchen and manager
- Item preparation states
- Ready and served transitions
- Waiter acknowledgment flow
- Order cancellation and rejection workflow
- Overdue order alerts
- Real-time event dispatch and consumer handling
- Reconnect and stale-event handling
- WebSocket authorization rules

Deliverables
- Kitchen dashboard
- Waiter order status flow
- Realtime order update system
- Audit trail for order events

Exit gate
- Order state changes persist and reflect in real time
- Duplicate/stale events are ignored
- Unauthorized subscriptions fail

Phase 5: Billing and payment MVP
Duration: 2 to 3 weeks
Goal: finalize bills, accept payments and manage refunds safely.

Tasks
- Table bill creation and finalization
- Immutable bill version logic
- Cash payment recording by cashier
- One online payment provider integration
- Payment intent creation and transaction verification
- Webhook validation and duplicate handling
- Refund request and approval flow
- Payment reconciliation logic
- Receipt generation from bill snapshots

Deliverables
- Bill finalization flow
- Cash and online settled payment workflow
- Payment status tracking
- Refund module
- Receipt output

Exit gate
- Duplicate webhooks settle once
- Failed payments leave bill unpaid
- No overpayment from concurrent payment attempts

Phase 6: Staff mobile app and role-based operations
Duration: 2 to 3 weeks
Goal: provide a usable mobile staff app for kitchen and service tasks.

Tasks
- Build Capacitor project and Android packaging
- Setup secure login for staff users
- Branch selection and context switching
- Dashboard for manager and cashier
- Table detail and order creation flows
- Ready items and service request handling
- Push notification setup and permission handling
- Android compatibility and device checks
- Staff session revocation and logout

Deliverables
- Android staff app MVP
- Role-based mobile navigation
- Secure staff auth flow
- Mobile push and notifications

Exit gate
- Staff can view assigned tables and complete core actions on Android
- Sensitive actions remain protected by backend policies

Phase 7: Platform admin and subscription management
Duration: 2 weeks
Goal: manage restaurants, plans, audits and reporting.

Tasks
- Restaurant moderation and approval/suspension
- Plan and subscription assignment
- Usage tracking for branches, staff and tables
- Subscription expiry controls
- Support ticket and audit log views
- Revenue and operational reports
- Export features for reports and records

Deliverables
- Platform admin dashboard
- Restaurant lifecycle control
- Subscription management
- Reports and audit visibility

Exit gate
- Platform can approve, monitor and support restaurants
- Food revenue remains separate from platform subscription billing

Phase 8: QA, security hardening and pilot launch
Duration: 2 to 3 weeks
Goal: stabilize the system before production pilot.

Tasks
- Security testing and auth bypass checks
- Cross-tenant access tests
- Payment race/duplicate webhook tests
- Real-time event recovery checks
- Session timeout, rate limit and abuse tests
- Load testing for restaurant and table traffic
- Data backup and restore drill
- Production deployment checklist
- Pilot restaurant onboarding and QA signoff

Deliverables
- Security test reports
- Performance results
- Backup and restore confirmation
- Pilot launch checklist
- Production runbook

Exit gate
- Critical vulnerabilities closed
- Pilot environment stable
- No critical payment or order integrity issue remains

Phase 9: Pilot and iteration
Duration: 2 to 4 weeks
Goal: validate business readiness with live usage.

Tasks
- Run pilot with one or two restaurants
- Monitor orders, queue delays and payment flow
- Resolve UX issues from real operations
- Tune performance and queue behavior
- Review staff feedback and operational bottlenecks
- Publish bug fix and improvement backlog

Deliverables
- Pilot report
- Prioritized improvement list
- Release readiness decision

Exit gate
- Stable operational metrics
- No unresolved critical issue for MVP release

Recommended MVP scope
- One branch per restaurant
- One payment provider
- Android staff app first
- QR customer ordering
- Order tracking
- Kitchen and waiter operations
- Bill finalization and payment
- Platform admin and reporting

Out of scope for MVP
- Multiple active branches per restaurant
- Automatic subscription billing
- Loyalty system
- Real-time deliveries
- Inventory and recipe costing
- POS printer integration
- Reservations
- Customer mobile app

Risk-based priority
Highest risk items must be built first:
- Tenant isolation
- Staff permissions and policies
- Table session locking
- Order idempotency
- Payment reconciliation
- Realtime event correctness
- QR token security

Suggested team structure
- 1 backend developer
- 1 frontend developer
- 1 mobile developer
- 1 QA / tester (part-time or shared)
- 1 product/UX support person (part-time)

Estimated total time
- MVP roadmap: 16 to 22 weeks
- Realistic delivery with a small team: 18 to 20 weeks

Definition of done for each phase
- Feature works in development environment
- Backend permission checks enabled
- Validation and test coverage added
- No cross-tenant data leakage
- Error/loading states handled
- API contract reviewed
- QA signoff done

Final recommendation
For this project, build the first version using Laravel + React + Capacitor as a modular monolith. Focus on the ordering and payment core first, then extend with admin, reporting and mobile flows. Avoid microservices and advanced modules until the MVP is operational and stable.

This phase-wise roadmap is designed to reduce delivery risk, improve QA quality and keep the team aligned around real product milestones.
